# 교과 평어 진행률·속도·생성 안정성 설계

## 목적

첨부 자료 분석과 평어 생성을 명확하게 분리하고, 교사가 현재 처리 상태와 완료 인원을 수치로 확인하도록 한다. 많은 학생의 평어는 두 묶음으로 동시에 생성해 대기 시간을 줄이며, 사소한 모델 출력 차이 때문에 전체 결과가 폐기되지 않도록 검증과 정제를 안정화한다.

## 확인된 원인

### 학생 목록 생성 후 버튼 비활성화

비밀번호가 입력된 상태에서 첨부 자료 분석이 끝나면 현재 코드는 `generateFrom(..., "all")`을 자동 실행하고 그 완료까지 기다린다. 표는 먼저 표시되지만 `isGenerating`이 유지되므로 생성 버튼은 자동 호출이 끝날 때까지 비활성화된다.

### 긴 생성 시간

현재 27명의 세 영역 평어를 하나의 OpenAI 요청으로 생성한다. 익명 합성 자료로 실제 호출한 결과 서버와 API 설정은 정상이며 약 32초가 걸렸다. 한 요청의 출력량이 크기 때문에 교사가 중간 완료 상태를 알 수 없고, 긴 실제 참고 자료에서는 출력 상한에 가까워질 수 있다.

### 실제 자료에서의 502 오류

현재 서버는 영역별 결과의 순서와 문장부호를 엄격하게 검사한다. 모델이 선택 영역을 모두 반환해도 순서가 달라지거나 한 영역에 마침표가 둘 이상 있으면 전체 결과를 거부한다. 또한 서버는 서로 다른 원인을 모두 `평어 생성 결과를 확인하지 못했습니다`로 반환하므로 사용자가 조치 방법을 알 수 없다.

## 자료 분석 흐름

1. `첨부 자료 분석`은 파일 읽기, 학생 명렬 추출, 영역 및 단계 추출까지만 수행한다.
2. 분석 성공 후 자동 평어 생성을 호출하지 않는다.
3. 학생 목록이 만들어지면 즉시 `isAnalyzing`을 종료하고 생성 버튼을 사용할 수 있게 한다.
4. 분석 중에는 다음 숫자를 표시한다.
   - 등록한 분석 대상 파일 수
   - 분석 경과 시간(초)
5. 완료 후에는 `학생 27명·영역 4개 추출 완료`처럼 결과 수치를 표시한다.

서버가 문서별 진행 이벤트를 제공하지 않으므로 분석 중 가짜 백분율은 사용하지 않는다. 파일 수와 실제 경과 시간만 표시한다.

## 평어 생성 흐름

### 요청 분할

- 대상이 12명 이하이면 기존처럼 한 묶음으로 생성한다.
- 13명 이상이면 학생을 앞뒤 두 묶음으로 균등 분할한다.
- 두 묶음은 서버에서 동시에 OpenAI에 요청한다.
- 브라우저에서는 `/api/generate-report`를 한 번만 호출하므로 IP 요청 제한을 여러 번 차감하지 않는다.

27명은 14명과 13명으로 나누며, 먼저 끝난 묶음부터 결과표에 반영한다.

### 스트리밍 응답

브라우저가 `Accept: application/x-ndjson`을 보내면 서버는 줄 단위 JSON 이벤트를 반환한다.

```json
{"type":"progress","completed":13,"total":27,"rows":[...]}
{"type":"progress","completed":27,"total":27,"rows":[...]}
{"type":"complete","usage":{"amountKrw":42,"budgetKrw":30000}}
```

기존 JSON 응답 방식도 유지해 기존 테스트와 다른 호출자가 깨지지 않게 한다.

### 화면 진행 표시

- 생성 시작: `0/27명 생성 중 · 0%`
- 첫 묶음 완료: `13/27명 생성 완료 · 48%`
- 전체 완료: `27/27명 생성 완료 · 100%`
- 숫자 진행률 막대에는 `role="progressbar"`, `aria-valuenow`, `aria-valuemax`를 제공한다.
- 진행 중에는 세 생성 버튼을 모두 비활성화해 중복 호출을 막는다.
- 완료된 묶음은 즉시 표에 표시하고 브라우저 세션 저장에도 반영한다.

## 생성 안정성

### 영역 검증

- 영역별 결과 개수는 선택 영역 수와 정확히 같아야 한다.
- 영역명 집합이 선택 영역 집합과 같아야 한다.
- 모델이 순서만 다르게 반환한 경우에는 거부하지 않고 서버가 입력 영역 순서로 재정렬한다.
- 영역이 누락되거나 중복되거나 추가된 경우 해당 묶음만 실패 처리한다.

### 한 영역 한 문장

- 프롬프트는 기존처럼 영역 하나당 한 문장만 요구한다.
- 모델이 같은 영역 문자열 안에 여러 마침표를 반환하면 빈 문장을 제거하고 각 절을 쉼표로 연결해 최종 마침표 하나인 문장으로 정제한다.
- 정제 후 내용이 비어 있으면 오류로 처리한다.

### 출력 길이

- 출력 토큰 상한은 학생 수뿐 아니라 학생 수 × 반영 영역 수를 기준으로 계산한다.
- 두 묶음 각각에 충분한 상한을 주되 요청당 서버 최대치는 유지한다.
- 영역별 문장은 지나치게 길지 않은 한 문장으로 작성하도록 프롬프트를 강화한다.

## 오류 처리와 비용 기록

- 인증, 비밀번호, 월 한도, 요청 제한 검사는 스트리밍 시작 전에 수행한다.
- 성공한 묶음의 토큰 사용량과 비용은 묶음 완료 시 각각 저장한다. 다른 묶음이 실패해도 실제 발생한 성공 비용을 누락하지 않는다.
- 한 묶음이 실패하면 이미 완료된 결과는 표에 유지한다.
- 실패한 학생 수와 안전한 오류 유형을 화면에 표시한다.
- 서버 로그에는 학생 이름, 원문, 프롬프트, 생성 평어를 기록하지 않는다.
- 로그에는 오류 코드, 모델, 묶음 학생 수, OpenAI 상태 코드만 기록한다.

사용자 메시지는 다음처럼 구분한다.

- 출력 길이 초과: `생성 결과가 길어 일부 학생을 처리하지 못했습니다. 남은 학생만 다시 생성해 주세요.`
- 영역 누락·중복: `일부 학생의 영역별 평어 형식이 맞지 않습니다. 남은 학생만 다시 생성해 주세요.`
- OpenAI 사용 제한: `요청이 많아 잠시 처리하지 못했습니다. 잠시 후 다시 시도해 주세요.`
- 서버 설정: `서버 설정을 확인해 주세요.`

## 비용과 성능의 절충

두 묶음이 평가 계획과 수행평가지 참고 내용을 각각 받아 입력 토큰 비용이 기존 한 요청보다 증가할 수 있다. 대신 출력 생성이 동시에 진행되어 전체 대기 시간을 줄이고, 한 묶음 오류가 전체 27명 결과를 없애는 문제를 피한다. 묶음 수는 최대 두 개로 제한해 비용 증가와 OpenAI 요청 제한 위험을 통제한다.

## 테스트 기준

1. 비밀번호가 있어도 첨부 자료 분석 뒤 자동 생성 API를 호출하지 않는다.
2. 분석 완료 즉시 생성 버튼이 활성화된다.
3. 분석 중 파일 수와 경과 시간이 표시되고 완료 후 학생·영역 수가 표시된다.
4. 12명 이하는 한 묶음, 27명은 14명과 13명 두 묶음으로 나뉜다.
5. 먼저 완료된 묶음마다 `13/27`, `27/27` 진행 이벤트가 전달된다.
6. 진행 이벤트를 받을 때 해당 학생 평어가 즉시 표에 반영된다.
7. 영역 순서만 다른 응답은 입력 순서로 재정렬해 성공한다.
8. 여러 마침표가 있는 영역 평어는 마침표 하나인 문장으로 정제한다.
9. 영역 누락·중복은 해당 묶음 오류로 분류한다.
10. 모든 생성 버튼은 생성 중 비활성화된다.
11. 성공한 묶음의 사용량은 다른 묶음 실패 여부와 관계없이 저장된다.
12. 로그와 응답에 학생 이름이나 입력 원문이 포함되지 않는다.

## 변경 범위

- `components/ReportGenerator.tsx`: 자동 생성 제거, 분석 타이머, 스트림 읽기, 진행률 및 부분 결과 반영
- `app/api/generate-report/route.ts`: 스트리밍 모드, 두 묶음 병렬 생성, 안전한 오류 이벤트와 묶음별 사용량 저장
- `lib/openai.ts`: 영역 순서 재정렬, 문장 정제, 영역 수 기반 출력 상한
- `lib/prompt.ts`: 간결한 영역별 한 문장 지시 강화
- `app/globals.css`: 진행률 표시 스타일
- 관련 Vitest 테스트

인증 방식, 승인 사용자 권한, 학생 익명화, 데이터베이스 모델, 월 예산 기준, 브라우저 세션 저장 범위는 변경하지 않는다.
